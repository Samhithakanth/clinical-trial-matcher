# TrialMatch – Clinical Trial Matcher

Next.js + MySQL dashboard for patients, clinical trials, match results, and audit history.

## Setup (Windows PowerShell)
1. Extract the ZIP and open PowerShell in `TrialMatch_Complete`.
2. Run `npm install`.
3. Run `Copy-Item .env.example .env.local`.
4. Edit `.env.local` with your MySQL credentials and a random `SESSION_SECRET` (see `.env.example`). Never share or commit this file.
5. Ensure MySQL80 is running, then run `npm run dev`.
6. Open http://localhost:3000.

## Pages
`/` Dashboard · `/patients` Patients · `/clinical-trials` Clinical Trials · `/matches` Match Results · `/audit` Audit Logs.

## Database tables/columns expected
- `patients`: subject_id, gender, anchor_age, anchor_year, anchor_year_group, unit_id
- `clinical_trial`: trial_id, nct_id, title, phase, status, conditions, minimum_age, maximum_age, sex, enrollment
- `match_result`: match_id, subject_id, trial_id, scalar_score, semantic_score, final_score, eligibility_status, matched_at
- `audit_log`: audit_id, table_name, record_id, action_type, changed_by, action_time, old_values, new_values

The API uses the singular core tables. The MySQL account needs SELECT on these tables; Audit Logs also needs SELECT on `audit_log`.

## Scope note
This UI displays values stored in MySQL. Note embeddings and `semantic_score` are generated by the embedding API below; `final_score` is not calculated. NULL scores display as “Not calculated”. Audit logs are trace records, not tamper-proof against a privileged database administrator.

## Note embeddings and semantic search

`clinical_notes.note_embedding` holds a 384-dimension sentence embedding of each note, generated locally with `all-MiniLM-L6-v2` (via `@huggingface/transformers`, so no API key is needed and note text stays on the machine). MySQL 8.0 has no vector type, so vectors are stored as JSON arrays and cosine similarity is computed in the API layer.

### Setup

```powershell
npm install @huggingface/transformers
Get-Content sql\002_note_embeddings.sql | mysql -u root -p clinical_trial_matcher
npm run dev
```

The app account needs SELECT and UPDATE on `clinical_notes`, SELECT/INSERT/UPDATE on `trial_embedding`, and UPDATE on `match_result.semantic_score` (granted in the SQL file). If your column names differ from the defaults, set them in `.env.local` (see `.env.example`). The first embedding call downloads the model (~23 MB) once.

### Endpoints

| Method | Endpoint | What it does |
| --- | --- | --- |
| GET | `/api/embeddings/notes` | Counts of embedded vs pending notes |
| POST | `/api/embeddings/notes?limit=100` | Embeds pending notes into `note_embedding` (repeat until `pending` is 0; `force=true` re-embeds all) |
| GET | `/api/search/notes?q=...&k=5` | Semantic search: notes most similar to the query text |
| GET | `/api/search/notes?trial_id=3&k=5` | Notes most similar to a trial's inclusion criteria |
| POST | `/api/matches/semantic-score[?match_id=5]` | Writes `match_result.semantic_score` = cosine(patient notes, trial title + inclusion criteria), clamped to 0–1 |

```powershell
Invoke-RestMethod -Method Post "http://localhost:3000/api/embeddings/notes?limit=200"
Invoke-RestMethod "http://localhost:3000/api/search/notes?q=type%202%20diabetes%20on%20metformin"
Invoke-RestMethod -Method Post "http://localhost:3000/api/matches/semantic-score"
```

After scoring, the Match Results page shows the semantic score instead of “Not calculated”.

### Limits

- `semantic_score` is a ranking signal for clinician review. It does not change `eligibility_status`, which stays with the rule-based `evaluate_match` procedure.
- Exclusion criteria are not embedded, so a note that mentions an excluded condition cannot raise the score; but similarity alone cannot detect exclusions either.
- Search is a brute-force scan, suitable for prototype-scale data. A larger deployment would move to MySQL 9 `VECTOR`, pgvector or a dedicated vector database with an ANN index.
- `all-MiniLM-L6-v2` is a general-domain model, not clinically validated.

## Sign-in and role-based access

Every page and API route requires signing in, except `/login`. Sessions are an HttpOnly cookie signed with HMAC-SHA256 (`SESSION_SECRET`) and last 8 hours. Passwords are stored only as scrypt hashes. Five failed attempts lock an account for 15 minutes, and every sign-in, failure, lockout, logout and account change is written to `auth_event`.

### Setup

```powershell
Get-Content sql\003_auth.sql | mysql -u root -p clinical_trial_matcher
# add SESSION_SECRET to .env.local (command to generate one is in .env.example)
node --env-file=.env.local scripts/create-user.mjs admin ADMIN "System Admin"
npm run dev
```

Sign in at http://localhost:3000/login as `admin`, then create the other accounts on **Access & Security**. `create-user.mjs` can also reset a forgotten password.

### Roles

Web app roles mirror the database roles (`attending_clinician_role`, `clinical_researcher_role`, `compliance_officer_role`).

| Page / API | ADMIN | CLINICIAN | RESEARCHER | COMPLIANCE |
| --- | --- | --- | --- | --- |
| Dashboard, Clinical Trials | ✓ | ✓ | ✓ | ✓ |
| Match Results | ✓ | ✓ | ✓ (patient age hidden) | ✓ |
| Patients, note search, embeddings, semantic scoring | ✓ | ✓ | – | – |
| Audit Logs | ✓ | – | – | ✓ |
| Access & Security: sign-in activity | ✓ | – | – | ✓ |
| Access & Security: manage accounts | ✓ | – | – | – |

Rules live in `src/lib/access.ts` and are enforced in `src/middleware.ts` for every request: pages redirect to `/login` or `/forbidden`, APIs return 401 or 403. Cross-site POST/PATCH requests are rejected. The sidebar only shows pages the role may open. Account changes (role change, disable, password reset) end that user's sessions on the next page load; admin actions re-check the database on every request.

### Limits

- The app still connects to MySQL with one account (`DB_USER`), so access between web roles is enforced by the app, not by MySQL grants. Connecting with one MySQL account per web role would add database-level enforcement.
- Audit triggers record the MySQL account in `changed_by`, not the signed-in web user.
